# H - Pixel-art restyling of Evolve's interface (feasibility and specification)

Status: read-only analysis. **Nothing was executed** (no game, no browser, no compilation). All line numbers come from `src/` (not from `evolve/evolve.css`, which is minified). Claims marked *(unverified)* are deductions to be confirmed on the phone.

Companion file: `project-docs/audit/H-prototype-theme-pixel.css` (commented prototype, not applied).

## 0. Verdict

Feasible, without touching the game logic, in three layers:
1. a **separate CSS file** `evolve/pixel.css`, loaded after `evolve.css`, activated by an **attribute** `<html data-skin="pixel">` (not a class: see trap 1);
2. a **small JS generator** that, once the kit is loaded, converts pieces (`ui_button`, `ui_panel`, `ic_*`) into data URIs and sets them in CSS variables;
3. a **pixel font** generated from the kit's glyphs (no dependency) or, failing that, titles only.

The three traps the code reveals, which change the plan:
- **Trap 1 - `html.pixel` would be erased.** `setTheme()` does `$('html').removeClass()` then adds the theme and the font (`src/index.js:138-143`). Any class added to `<html>` disappears on the first theme change. Solution: `data-skin` (attributes are not touched), or `body.pixel`.
- **Trap 2 - there is no `is-disabled` class for actions.** The "affordable" state is read on the `.action` container: `cna` / `cnam` (see section 3).
- **Trap 3 - `evolve.css` is not rebuilt** by the fork (`README-FORK.md`: "The CSS is not rebuilt"). Modifying `evolve.less` would force compiling LESS (there is `lib/less.3.9.min.js` browser-side, but the build is not wired up). A separate CSS override is therefore clearly safer and does not touch the upstream sources.

### 1.3 Existing themes (not to be broken)

Ten themes as a class on `<html>`: `dark`, `light`, `night`, `redgreen`, `darkNight`, `gruvboxLight`, `gruvboxDark` (default, `vars.js:1315`), `gruvboxDarkRG`, `orangeSoda`, `dracula` (`evolve.less:1853-2335`). Each theme fills the same LESS variables then the rules are emitted under `html.<theme> ...`, typical specificity `(0,5-7,2)`. The skin must **not** remove these text colours (`has-text-*`), because they carry meaning (red = danger, etc.): it only replaces frames, button backgrounds, bars and typography.

## 2. Restyling mechanism

### 2.1 Wiring

- `index.html`: add after `evolve/evolve.css` a `<link rel="stylesheet" href="evolve/pixel.css">` and `<html data-skin="pixel">` (or set it from `anki-village.js`, which is already the fork's entry point). A user setting (localStorage `avSkin`) allows going back to the original interface: the skin must be **disableable** by removing the attribute.
- Why a separate file and not `evolve.less`: (a) the CSS is not rebuilt, (b) a separate file survives Evolve updates (we replace `src/` without losing the skin), (c) trivial rollback.
- Specificity: two useful rules. (1) `html[data-skin="pixel"] .button` is (0,2,1), like `html.dark .button`; loaded afterwards, it wins. (2) for the game's deeper rules (`html.dark .main .content .action a.button...`), take the same path adding `body`. Last resort: `!important`, to be avoided.
- Beware of the `transition: all 200ms ease` (`.button` 2387, `a` 2394): they blur pixel state changes; the prototype cuts them.

### 2.2 Pixel images at load time (data URI)

The kit already knows how to draw everything; it only needs to rasterise. Useful findings:

- `X.sprite(name, map, opt)` returns a `Pix`; `Pix.prototype.canvas()` (`spritekit.js:41`) creates a `<canvas>` of the exact size; `canvas.toDataURL('image/png')` gives the data URI. `X = SpriteKit._` (`spritekit.js:628`), accessible as long as `SpriteKit.isReady()` is true (`anki-village.js:61` already uses it).
- **`ui_button` (16x16, `slice: 5`) and `ui_panel` (24x24, `slice: 8`) are already 9-slice sources.** No need for `SK.ui.nine`: the raw piece directly becomes `border-image-source`, with `border-image-slice: 5 fill` (button) or `8 fill` (panel). `SK.ui.nine/button/panel` are only for fixed sizes (useful for a precise button icon).
- Variants: the 2nd argument (`{ MAIN:'saffron', ACCENT:'cream' }`) recolours. The states (`hover` = 1 tone lighter, `pressed` = 1 px lower / 1 tone darker) exist in `SK.ui.button(..., state)`; in CSS, we prefer the **same** template + `transform: translateY(var(--u))` for `:active`, which avoids 3 images per variant.
- Sketch (to be placed in a `skin-pixel.js` loaded after `anki-village.js`, **untested**):

```js
function px(name, map) {                 // -> 'url(data:image/png;base64,...)'
  var X = SpriteKit._, cv = X.sprite(name, map).canvas();
  return 'url(' + cv.toDataURL('image/png') + ')';
}
function buildSkin() {
  var r = document.documentElement.style, ui = 'ui_button';
  r.setProperty('--px-btn-main',  px(ui, { MAIN: 'saffron', ACCENT: 'cream' }));   // primary
  r.setProperty('--px-btn-alt',   px(ui, { MAIN: 'hide',    ACCENT: 'cream' }));   // secondary
  r.setProperty('--px-btn-quiet', px(ui, { MAIN: 'cream',   ACCENT: 'cream' }));   // tertiary
  r.setProperty('--px-btn-danger',px(ui, { MAIN: 'madder',  ACCENT: 'cream' }));   // danger
  r.setProperty('--px-btn-off',   px(ui, { MAIN: 'ashen',   ACCENT: 'ashen' }));   // disabled
  r.setProperty('--px-btn-busy',  px(ui, { MAIN: 'teal',    ACCENT: 'cream' }));   // in progress
  r.setProperty('--px-panel',     px('ui_panel', { MAIN: 'straw', ACCENT: 'cream', WOOD: 'oak' }));
  // resource icons: 16x16 -> data URI, one variable per resource
  var T = SpriteKit.era1 ? SK.RES_ICON : {};   // Food, Lumber, Stone, Furs, Copper, Iron, Cement, Coal, Steel, Money, Knowledge...
  for (var k in T) r.setProperty('--px-ic-' + k, px(T[k][0], T[k][1]));
  document.documentElement.setAttribute('data-px', 'ready');   // switches layer A -> layer B
}
(function wait(){ if (window.SpriteKit && SpriteKit.isReady && SpriteKit.isReady()) buildSkin(); else setTimeout(wait, 300); })();
```

  (`SK` is `window.SK`, `SK.RES_ICON` is in `era1.js:49-54`; the exact shape of the object exposed outside remains to be confirmed.)
- CSS usage: `border-image: var(--px-btn-main) 5 fill / calc(5*var(--u)) / 0 round;` with an integer `--u` (2px or 3px) and `image-rendering: pixelated`. `round` (rather than `stretch`) avoids distorting the middle because the kit's `nine()` repeats the middle.
- **Pixelated rendering of border-image / background-image**: `image-rendering: pixelated` applies to background images, borders and `<img>`. Chrome and Firefox support it *(unverified on the user's device)*.
- Sequence: layer A CSS (without images) is displayed immediately; when `data-px="ready"` appears, layer B takes over. No blank page if the kit fails to load.
- Weight: a 16x16 PNG button is under 400 bytes; 6 variants + panel + 16 icons = about 10 to 15 KB in base64, injected **only once** into the `style` of `<html>` (CSS variables), not into every element. Performance: negligible. Risk to watch: `border-image` is repainted at every `class` change (`cna` changes at every tick when resources move); the images being cached, the cost stays low, but **to be measured on an entry-level phone**.
- Special cases:
  - **`<progress>` bars**: the `SK.ui.progress(w, frac)` piece has a fixed width, unusable as is. Make a 3-pixel frame + a `repeat-x` fill tile: frame with `border-image`, `::-webkit-progress-value` / `::-moz-progress-bar` with a tiled `background-image` (prototype: gradient repeated in pixel steps).
  - **Resource bar `.resource.showBar`**: only `--percent-full` exists, but only if `bar` is active (`resources.js:840`); we replace the soft gradient with a hard edge (done in the prototype). Showing the bar on every resource would require touching `resources.js`: out of scope.
  - **Icons**: `.resource .res::before { content:''; width:calc(16*var(--u)); height:...; background:var(--px-ic-Food) center/contain no-repeat; image-rendering:pixelated; display:inline-block; }` on `#resFood h3.res` (identifier `res<Name>` = resource key). The kit only has icons for **16 Era 1 resources** (`RES_ICON`: Food, Lumber, Stone, Furs, Copper, Iron, Cement, Coal, Steel, Money, Knowledge, Plywood, Brick, Wrought_Iron, Sheet_Metal, Aluminium) plus the `ic_*` (house, tent, face, head, morale, book, ...); for the others (RNA, DNA, future resources), plan a colour dot (`.has-text-*`) or nothing. **No new drawing is needed for Era 1; afterwards yes.**
  - **Tab icons**: `tab_gear`, `tab_card` exist. The `nav.tabs li` are indexed by position (`:nth-child`); since some are hidden (`:visible`), fragile; do not rely on the order without testing *(unverified)*. Robust alternative: a small script that reads the text of the `a` via the game's translation key.

### 2.3 Pixel font for HTML text

The kit has a bitmap (`ui_font`: 8x10 cell, ~100 glyphs including French accents, `€`, `«»`, variable widths, `pieces_b7.js:71-81`). It is not a web font. Options:

| Option | Feasible offline without dependency? | Licence | Limits |
|---|---|---|---|
| **A1. Generate a real font (TTF/WOFF) from the kit's glyphs**, either at build time (dependency-free Node script, ~200 lines writing the `head, hhea, maxp, hmtx, cmap fmt.4, loca, glyf, name, post, OS/2` tables, each pixel = a square outline), or at load time (`new FontFace('KitPixel', bytes)` + `document.fonts.add`) | Yes, 100% offline. It is the option that matches the kit's style exactly. | The drawings are the project's own (no third-party licence) | Medium effort (~1 d); crisp rendering only at multiples of the cell (em = 10 px: 10, 20, 30 px); a bug in a table = font silently rejected, so to be tested on device; coverage limited to ASCII + French, the rest falls back to the next font in the stack (acceptable) |
| A2. SVG font (`<font>` SVG) | Yes in theory | - | **Dropped by Chrome and Firefox**, does not work: to be ruled out |
| A3. Titles rendered as images (canvas -> data URI) | Yes | - | Dynamic text (translations, numbers) impossible, accessibility and selection lost; usable only for 3-4 static titles |
| A4. System monospace stack + `image-rendering` | Yes | - | `image-rendering` does not apply to text: no pixel effect |
| **A5. Free font embedded in base64** (examples in common use: *Press Start 2P* OFL 1.1, *Silkscreen* OFL, *VT323* OFL, *Pixelify Sans* OFL, *Tiny5* OFL, *Monogram* CC0, *m5x7* author Daniel Linssen, free with credit) | Yes once the file is downloaded (I downloaded **nothing**, licences cited from memory, to be rechecked) | OFL permits embedding, with the licence | Several are distributed through Google Fonts: the "nothing from Google" rule targets the service, but a non-Google download source will be needed (the author's repository); accent coverage varies; Press Start 2P is very wide (bad for a resources column at 360 px) |
| B. Pixel only for titles and numbers | Compatible with A1 or A5 | - | **Recommended**: paragraphs, popovers and the log stay in `system-ui` for legibility and for languages not covered |

Recommendation: **A1 + B**. CSS stack: `font-family: "KitPixel", ui-monospace, monospace;` only on titles (`h2`, `.tabs a`, `.aTitle`, `.res`, `.count`, `.diff`, job names). Integer size (20 px = 2x). If `KitPixel` is not available, falls back to monospace: the interface remains usable.

## 4. Mobile

### 4.1 Why the original interface is unusable

- `html { overflow-y: hidden }` (`evolve.less:2342`) and `.main { overflow-y: hidden }` (2606): **the page does not scroll**.
- Heights in `calc(100vh - N rem)`: `.leftColumn` 2609, `.msgQueue.right` 2695, `.resTabs>section` 2786, `.govTabs2>section` 2790, `.resources` 2796/2799, `.content .settings` 2865, `.mtab` 2891, `#hellTabs>section` 3459, `.hellReports>div` 3467, `#hellAnalysis` 3533, `.modal .modalBody` 4174, `.sticky` (100vh) 5273, `#evolution` 5295.
- Fixed widths in rem: `.action a.button` 12.625rem (~202 px); `.job` `min-width: 18rem`; `.industry` 27.5rem; `.arpaProject` 20rem; `.modal .modal-content{min-width:42rem}` (5304, 672 px > screen).
- `.topBar` and `.promoBar` are `position: fixed` (4495): they eat the top and the bottom.
- Bulma does stack columns below 769 px (`.columns` is `display:flex` only at >= 769 px), so **the one-column layout almost already exists**; it is hidden by the rules above.
- `resizeGame()` (`vars.js:2049`) moves the queues to the right only at >= 1400 px: irrelevant on a phone.
- The game has a `touch` setting (`index.js:1416`) for touch tooltips, but the test `navigator.userAgent.match(/Mobi/ && global.settings.touch)` (`functions.js:72, 91`) is badly parenthesised (`/Mobi/ && ...` evaluates the `&&` first): the rule is probably always "/true/" *(to dig into, unverified, out of scope)*. To test: popovers on touch; a game-side fix may be needed.

### 4.2 Proposed layout (<= 768 px)

| [ village view  (30vh) v ]   |  village panel IN FLOW, collapsed by default at 22vh, full-screen button
+------------------------------+

- **Scrolling**: unlock `html { overflow-y: auto }`, `.main { overflow: visible }`, switch all the `calc(100vh...)` heights of 4.1 to `height:auto`, `.sticky { position: static }`. Internal scrolling only for `.resources` (max 40vh) and `.msgQueue`/`.bldQueue`.
- **Touch targets >= 44 px**: `a.button` at `min-height: 44px`; `.add`/`.sub` 44x44; tabs 52 px. Exception: the `.count` badge, the `div.special` cogwheel and `span.on/off` are **small dots overlaid on the corners** of the button (height 1.0625 rem): 44 px is impossible there without moving them; the prototype sets them to 32x28 and this point remains an **open doubt** (option: move them below the button, inline).
- **Bottom tabs**: `#mainTabs > nav.tabs` at `position: fixed; bottom: 0`. The exact structure `div.b-tabs#mainTabs > nav.tabs` is Buefy 0.9.22's *(not verified in the generated DOM)*. The `.resTabs` sub-tabs stay at the top of the content, scrolling in x.
- **Village panel**: today `#av-panel` is `position:fixed; bottom:0; height:42vh` (`anki-village.js:13`) and collides with a bottom tab bar. To change: put it **at the top, in flow** (just under `#topBar`) with 22 to 30vh and an "enlarge" button, or anchor it **above** the tab bar. Both are small changes in `anki-village.js` (not in the game logic). Guard: `pickScale()` uses `panel.clientWidth` so it follows.
- **Modals**: `.modal-content` becomes `min-width:0; width:calc(100vw - 1rem)`.
- **Zoom**: do not block pinching (`index.html` has no `user-scalable=no`, good); `body{touch-action:manipulation}` already exists (`evolve.less:2356`).
- **Landscape orientation**: above 768 px, the game goes back to its column layout; do not rewrite it.
- **Safe areas**: `env(safe-area-inset-bottom)` on the tab bar (notches).

## 6. Risks and doubts

| Risk | Severity | Mitigation |
|---|---|---|
| Nothing is tested; `border-image` + `image-rendering:pixelated` + `fill` not verified on the user's browser | high | step 0; layer A usable without images |
| `setTheme()` erases the classes of `<html>` | high (certain) | use `data-skin` |
| Maintenance if Evolve updates (classes `cna/cnam/action`, Buefy structure) | medium | skin in a separate file, selectors documented in this report; check `actions.js:6224-6330` and `main.js` at each update; the fork is based on a fixed 1.4.10 |
| Existing themes (10) | medium | the skin does not replace `has-text-*`; test text/background contrast per theme; the themes' `@cnam-aTitle` may be unreadable on a light background (handled by `color:inherit`, to be verified) |
| Contrast / accessibility | medium | WCAG AA (4.5:1) to be measured; **never carry state by colour alone** (hatching on `cnam`, dotted outline on `hl`, bold on the primary); keep the game's `aria-label`s (no text removed); explicit `:focus-visible`; `prefers-reduced-motion` |
| Pixel font: legibility, languages not covered | medium | titles/numbers only, `system-ui` fallback; sizes multiple of 10 px |
| Performance: `border-image` repainted at every tick (`cna` changes) and scrolling of long lists | medium | CSS variables (no repeated data URI), avoid multiple `box-shadow` on the 100+ buttons if slow; measure on a modest phone |
| Data URIs in CSS variables | low | ~15 KB in total; set via `style.setProperty`, no duplication |
| Loading: asynchronous kit (`anki-village.js:76-78`) | low | layer A first, then `data-px=ready` switch |
| Touch targets of the corner dots (<44 px) | medium | open doubt, see 4.2 |
| The `touch` setting / touch popovers may be broken by a badly parenthesised test (`functions.js:72`) | medium, outside the skin | to be verified on device, fix on the game side |
| Non-Era 1 resources without an icon | low | colour dot or nothing; drawing on demand |

### What is not verified
Nothing was executed. In particular: the exact DOM generated by Buefy (`#mainTabs > nav.tabs`), the rendering of pixelated `border-image`, the reliability of `:nth-child` for tab icons, the presence/absence of Font Awesome at runtime, the feasibility of the generated TTF font (not written), the exact API exposed by the kit outside `SpriteKit._` (`SK` global), the licences cited for free fonts (from memory), the residual overflows of all non-Era 1 views, the compatibility of the CSS prototype with the 10 themes.

## 7. Recommendation

1. Do **step 0** (static test bench) then **step 1**: this is the part that makes the game playable on a phone, independently of the pixel aesthetics.
2. Add the **generated font (A1)** and the **kit images (step 2)** afterwards: this is where the pixel/bohemian universe appears.
3. Keep the skin **optional** (`data-skin` attribute) to go back to the original interface in case of trouble.
4. Do not touch `src/*.js` nor `evolve.less`; the only fork files to modify: `index.html` (CSS link + attribute) and `anki-village.js` (village panel position, loading of the generator).
